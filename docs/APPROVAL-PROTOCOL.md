# Tapproved approval protocol v1

This document defines the exact byte sequence signed by the registered Ed25519 device key. The contract reconstructs the message from stored payment state; a relay must never be trusted to supply the message fields used for on-chain verification.

## Encoding

The byte sequence is concatenated in this exact order:

1. Domain separator: ASCII `TAPPROVED`, followed by byte `0x00`, followed by version byte `0x01`.
2. Contract account ID: UTF-8 bytes prefixed by a 4-byte unsigned little-endian byte length.
3. Network ID: UTF-8 bytes prefixed by a 4-byte unsigned little-endian byte length.
4. Payment ID: unsigned 64-bit little-endian integer.
5. Recipient account ID: UTF-8 bytes prefixed by a 4-byte unsigned little-endian byte length.
6. Amount: unsigned 128-bit little-endian integer in yoctoNEAR.
7. Nonce: unsigned 64-bit little-endian integer.
8. Expiry: unsigned 64-bit little-endian block timestamp in nanoseconds.

No JSON serialization, separators, null terminators for strings, floating-point amounts, or display-formatted NEAR amounts are included.

## Shared test vector

`protocol/v1-vector.json` is the normative deterministic interoperability fixture. It contains the input fields, expected encoded bytes, public key, and Ed25519 signature. The corresponding private seed is deliberately not committed. The fixture deliberately uses the deterministic test account `tapproved.testnet`; this is protocol test data, not the deployed contract ID. The live deployment and firmware/relay configuration use `manextech.testnet`.

The Node test suite verifies byte-for-byte encoding and Ed25519 signature verification, then confirms that changing the amount invalidates the signature. Firmware CI compiles the same pure C++ encoder used by `main.cpp`, feeds it the fixture inputs and compares every output byte with `message_hex`; it also verifies rejection of leading-zero and out-of-range numeric fields. Contract tests consume the same fixture and verify its signature.

## Security requirements

- Sign only data obtained from the contract's payment record and verify that the contract ID and network match the configured deployment.
- Show the recipient and amount to the human before accepting physical approval. A serial-only prototype is not suitable for blind signing in production.
- Never log, transmit, or commit the private key.
- The relay transports requests and signatures; it is not an authority.
- The v1 format is immutable. Any incompatible change requires a new domain version and fixture.


## USB serial transport envelope v1

The serial envelope is distinct from the signed approval-message format above. The envelope version does not alter the v1 signature bytes.

Each request is one UTF-8 JSON object followed by a single LF byte. CRLF input is tolerated by the relay. The maximum request or response line is 2,048 bytes. The relay permits one outstanding request per serial connection and applies a bounded approval timeout.

A request contains:

- `frame_version`: integer `1`.
- `request_id`: a UUID v4 generated by the relay for this approval attempt.
- `contract_id`, `network_id`, `agent_id`, `status`, `payment_id`, `recipient_id`, `amount_yocto`, `nonce`, and `expires_at_ns`: the payment context from the canonical contract view. The device requires the canonical agent and `pending` status, a valid 2–64 character NEAR account ID, positive payment ID/amount/expiry, and canonical unsigned decimal strings within the u64/u128 field ranges.

A device response echoes the exact `frame_version` and `request_id`. Signed responses additionally contain the 32-byte `public_key_hex` and 64-byte `signature_hex`. Rejection and device-error responses also echo the request ID when the envelope can be parsed.

The relay accepts a signed response only when its frame version and request ID match the currently outstanding request. Responses for timed-out, disconnected, completed, or otherwise stale request IDs are ignored. A new physical approval attempt always receives a fresh request ID. The request ID is transport correlation metadata and is not part of the signed approval message; the contract continues to verify only the canonical payment fields.
